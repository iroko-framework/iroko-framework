Technical Architecture

System design, URI strategy, and deployment infrastructure

Overview

The Iroko Framework separates vocabulary publication (what terms mean) from data publication (actual records). The GitHub Pages site at iroko-framework.github.io/iroko-framework publishes the vocabulary definitions. The operational archive — which holds actual sacred knowledge records — is governed by irokosociety.org with API-mediated access.

Vocabulary vs. Data Separation

The distinction is intentional and principled. Publishing the vocabulary openly (CC0) enables interoperability: any institution can adopt these terms, integrate with Darwin Core or SKOS systems, and describe their own holdings using a shared vocabulary. Publishing the data openly would expose sacred knowledge without community authorization.

The Iroko Historical Society publishes:

  • Full vocabulary (all classes, properties, concept schemes) — public, CC0
  • Minimal public data (scientific plant names, vernacular names) — public

The Iroko Historical Society does not publish:

  • Ritual use details, harvest protocols, preparation methods
  • Initiation records, initiate identities, witness lists
  • Operational ceremony sequences
  • Any records marked iroko:access-no-access

URI Strategy

Vocabulary terms (namespace URIs)

Vocabulary terms use https://www.irokosociety.org/iroko-framework/{module}# as the base namespace. These URIs are stable and permanent — changing a term's URI is a breaking change requiring a version increment.

iroko:  https://www.irokosociety.org/iroko-framework/core#
ewe:    https://www.irokosociety.org/iroko-framework/ewe#
nkisi:  https://www.irokosociety.org/iroko-framework/nkisi#
travay: https://www.irokosociety.org/iroko-framework/travay#
ile:    https://www.irokosociety.org/iroko-framework/ile#

Data instance URIs

Individual records (plant instances, house records, etc.) use https://www.irokosociety.org/iroko-framework/{module}/{ID}. The Ewé plant data currently uses ewe:Plant0001 through ewe:Plant000n as local identifiers in the pilot dataset.

Access Control Implementation

Access control in the Iroko Framework operates at the property level, not the record level. This means a single plant record can have some fields public (scientific name) and others restricted (harvest protocol). The iroko:minimumAccessLevel annotation on each property declares the minimum access tier required to see that field's value.

Implementing institutions enforce access in their application layer — the vocabulary itself documents the intent but cannot enforce it. The recommended pattern is to filter SPARQL results by access level before returning data to the client.

HTML Generation Pipeline

The vocabulary browse pages (iroko-core.html, etc.) are generated programmatically from the TTL source files using generate_browse_pages.py. The script uses rdflib to parse the TTL and renders classes, properties, and concept schemes into the shared HTML template.

TTL source → rdflib parse → Python render → HTML output
                 ↑                               ↓
         iroko-style.css              iroko-{module}.html

The HTML files are committed to the repository alongside the TTL — GitHub Pages serves both. When a TTL is updated, the corresponding HTML must be regenerated and committed in the same push.

Technology Stack

  • Vocabulary format: RDF/Turtle (OWL + SKOS)
  • HTML generation: Python 3 + rdflib
  • Hosting: GitHub Pages (static)
  • Styling: Pure CSS (Cormorant Garamond, DM Mono, DM Sans via Google Fonts)
  • External standards: Darwin Core, SKOS, Dublin Core, PROV-O, FOAF, schema.org

Future Module Planning

Five additional modules are in development: Marca (divination systems), Ékpè (sacred societies), Vèvè (graphic sign systems), Ngoma (sacred music), and Sankofa (reclamation movements). Each will follow the same TTL-first, generated-HTML pattern. When all ten modules are complete, the HTML generation pipeline will be automated via GitHub Actions to eliminate manual regeneration.
